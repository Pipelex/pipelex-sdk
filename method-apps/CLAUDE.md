# pipelex-method-apps

The family of Pipelex method templates: one directory per shape and language, each of which a project starts as a copy of. This directory is the family's root inside the `pipelex-sdk` repository, whose root `CLAUDE.md` also applies. The family root holds what belongs to the family, and [`docs/family.md`](docs/family.md) explains it.

## Layout

| Dir                | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webapp-js/`       | The Next.js 16 web app template, package `pipelex-method-webapp-js`: an app that renders each method's input form and result view from its contract. **Its own [`CLAUDE.md`](webapp-js/CLAUDE.md) is the guide for any work inside it.**                                                                                                                                                                                                    |
| `initializers/js/` | `@pipelex/create-method-app`, the npm initializer (`npm create @pipelex/method-app`): it carries the Node templates packed from `git ls-files`, writes one into a directory, makes the pristine commit and runs the copy's `make create`. Plain `.mjs` with no dependency, tested with `node --test`; its table of templates is its `templates.json`. `initializers/cases.json` beside it is the table of cases every initializer executes. |

The family root carries the gate (`Makefile`), the family's changelog (`CHANGELOG.md`), and the family's tooling with its tests (`scripts/`, which holds the templates to the create contract and to the initializers' tables). The repository's root carries what serves every package: the version (`VERSION`); the CI (`.github/workflows/ci.yml`, described in the root `docs/ci.md`), which runs the family's checks and calls the twins of the templates' workflows; those twins, rendered beside it in `.github/workflows/`; the scripts that check every manifest against `VERSION` and render the twins (`scripts/`), run by the root `Makefile`; the git hooks, which run each template's own pre-commit hook (`.githooks/pre-commit`); and the skills that move every template onto a newer form kernel or SDK (`.claude/skills/bump-mthds-form/`, `.claude/skills/bump-sdk/`). A release of the family is a release of the whole repository, cut from its root, and its merge into `main` publishes the initializer through the root's `.github/workflows/release.yml` (the root `docs/release-model.md`).

## Rules

- **A template directory must work on its own.** A project is a copy of that directory alone, so nothing in it may need the root: no import, script or config reaching above it. What a template says about this repository goes in a passage its bootstrap removes or a file its bootstrap replaces.
- **Work inside a template follows that template's `CLAUDE.md`**, and its gate runs the same from inside it or from here.
- **A workflow is edited in its template, then re-rendered.** After changing anything under `<template>/.github/workflows/`, run `make workflows` at the repository's root and commit the twins it renders into the root `.github/workflows/` with it. Never edit a twin, a file there that opens with `# Rendered by`: the root's `make check-workflows`, part of its `agent-check` and of the root CI, reports it as stale.
- **The family ships as one, at the repository's version.** Every template's manifest and the initializer's carry one version, the one the family last shipped as, at or below the root `VERSION`, and only a release moves them, together; the root's `make check-versions` fails otherwise. The root's `release.yml` publishes the initializer at the release's version whenever a release ships the family.
- **A template joins its ecosystem's initializer.** Every template in `TEMPLATES` is in exactly one initializer's `templates.json`, and a root test fails otherwise; the initializer's packs are generated (`npm run pack-templates` in `initializers/js/`) and gitignored.
- **Changelog entries go in the family's `CHANGELOG.md`**, the one in this directory, under `## [Unreleased]`. A template's own `CHANGELOG.md` only points here.
- **After any change, run `make all` in this directory**, or `make agent-test` for the tests alone, quiet on success. `make format` fixes a formatting failure, in the family root and in every template. After changing a workflow or a version, also run `make check-workflows check-versions` at the repository's root.
- **Pull requests target `dev`**; a `release/vX.Y.Z` branch targets `main`, and is cut for the whole repository from its root.
- **Adding a template** follows the steps at the end of [`docs/family.md`](docs/family.md).
